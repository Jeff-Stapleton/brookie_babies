# AGENT.md

Guidance for AI coding agents (and humans) working in this repository.

## What this is

**Brookie Babies** is a Flutter **web** app: a marketing and booking site for a
photography business. Visitors see a full-screen photo carousel, choose a
session package (Basic / Premium / Ultimate), pick a date and session time, and
are sent to a Stripe Payment Link to pay.

- Firebase project: `brookie-babies` (see `.firebaserc`)
- Hosting: Firebase Hosting, serving the static `build/web` output
- Stage: early MVP. Much of the content is placeholder (see "Known gaps").

Although the `android/`, `ios/`, `macos/`, `linux/` and `windows/` folders exist
(from `flutter create`), **only web is supported**:
`lib/firebase_options.dart` only configures web; every other platform throws
`UnsupportedError` at startup.

Always run and build with `-d chrome` / `flutter build web`.

## Tech stack

| Concern | Package |
|---|---|
| UI framework | Flutter 3.47.7 (Material 3), pinned in CI |
| Firebase bootstrap | `firebase_core` |
| Carousel images | `firebase_storage` (lists `gs://brookie-babies.firebasestorage.app/_admin/gallery`) |
| Calendar | `table_calendar` |
| Payments | Stripe Payment Links via `url_launcher` |
| Auth | `firebase_auth`: Google sign-in (popup) behind `AuthService` |
| Bookings | `cloud_firestore`: `bookings` collection, read-only for customers, behind `BookingService` |
| Photo downloads | `cloud_functions`: `getGalleryDownloadUrl` (in `functions/`) behind `GalleryService` |
| Backend | Cloud Functions for Firebase, TypeScript on Node 24 (`functions/`); Firestore and Storage security rules |
| Lints | `flutter_lints` (`analysis_options.yaml`, default rules) |

## User flow

1. `HomePage` → `CarouselExample` loads every file in Storage `_admin/gallery` and
   cross-fades through them every 10s. "Book Now" scrolls to the packages.
2. `Packages` → `PricingCard` "Book Now" → `Navigator.push(SchedulingPage(packageName))`.
3. `SchedulingPage` → user selects a day → tapping any `SessionCard` calls
   `navigateCheckout()`. Signed-out visitors get `showSignInDialog()` first
   (Google popup). It then opens the package's Stripe Payment Link
   (`services/payment_links.dart`) in the same tab, with
   `client_reference_id=<uid>` and `locked_prefilled_email=<email>` so the
   payment shows which account paid. This is interim: the plan is to replace
   Payment Links with Checkout Sessions created by a Cloud Function.

4. Account menu → "My sessions" (`ProfilePage`, also at `/#/profile`) lists the
   user's `bookings`, split into upcoming and past. A paid session with
   `photosReady: true` has "Download all photos" (past paid sessions without it
   say the photos are being edited): `getGalleryDownloadUrl`
   checks the booking belongs to the caller, zips `galleries/<bookingId>/` (cached
   in `gallery-zips/`), and returns a signed link that expires after an hour,
   opened in the same tab.

The account button (top right of the home page and in the scheduling page's app
bar) signs in and out at any time.

Nothing in the app creates bookings yet: the Payment Links don't carry the date
or time. Until server-created Checkout Sessions write them, the photographer
adds them by hand in the Firestore console (fields in the README).

A named route `/schedule` exists in `main.dart` but the main flow does not use
it (it passes an empty package name, which falls through to "Unknown package
type").

## Commands

```bash
flutter pub get                 # install deps
flutter run -d chrome           # run locally (web)
flutter analyze                 # lints
flutter test                    # tests (Dart VM)
flutter build web               # production build -> build/web
firebase deploy --only hosting  # manual deploy: run flutter build web first (build/web is what gets deployed)

# Cloud Functions (Node 24; on this Mac it's Homebrew's keg-only node@24)
npm ci --prefix functions       # install deps from package-lock.json
npm test --prefix functions     # tsc build + node:test unit tests
firebase deploy --only functions,firestore:rules,storage   # backend deploy by hand; CI does it on pushes to main
```

CI (`.github/workflows/ci.yml`) runs `flutter pub get --enforce-lockfile`,
`flutter analyze --no-fatal-infos`, `flutter test` and
`flutter build web --release` on Flutter 3.47.7. It fails if any tracked file
or `build/web` contains a Stripe secret key, webhook secret or private key. If
those pass, it deploys a preview channel for
pull requests and the live site for pushes to `main`. A separate `functions`
job runs `npm ci`, `npm run build` and `npm test` in `functions/`. On pushes
to `main`, `deploy-backend` deploys the functions and rules (keyless, through
Workload Identity Federation as `github-deployer`; a dry run until the
repository variable `BACKEND_DEPLOY_LIVE` is `true`), then `deploy-live`
deploys Hosting. The Hosting deploys use `--only hosting`. One-time setup:
`scripts/setup-gcp-deployer.sh` and `scripts/setup-github-production.sh`
(README, "Automatic backend deploys").

Storage CORS (needed for the carousel images to load in the browser):

```bash
gsutil cors set cors.json gs://brookie-babies.firebasestorage.app
```

## Conventions

- Imports in `lib/` use `package:brookie_babies/...`. Tests import shared
  helpers relatively (`../support/fakes.dart`).
- Widgets are mostly `StatelessWidget` with `const` constructors and `super.key`.
- Text styling goes through the `widgets/*_text.dart` wrappers rather than
  inline `TextStyle`s; reuse them.
- Put new screens in `pages/`, page sections in `components/`, reusable leaf
  widgets in `widgets/`.
- Logging uses `dart:developer`'s `log()`; `page_footer.dart` still uses `print`.
- Get services with `AppServices.of(context)`. Only `main.dart` touches
  `FirebaseAuth.instance`, `launchUrl` and `package:web`, so everything else can
  be tested with the fakes in `test/support/fakes.dart`.
- Call `signInWithGoogle()` as the first thing in a tap handler, before any
  `await`, or the browser may block the popup. Don't switch to redirect
  sign-in: the site (web.app) and auth domain (firebaseapp.com) differ, which
  breaks redirects in current browsers.

## Known gaps / gotchas

- **SECURITY: this repository is public.** A live Stripe secret key used to be
  hard-coded in `lib/main.dart` and was also committed inside `build/` and
  `.dart_tool/` output. It has been removed from the tracked files but remains in
  git history, so it must be rolled in the Stripe dashboard. Never add secrets,
  service account keys or Stripe keys to this repo; server-side secrets belong in
  Secret Manager (`firebase functions:secrets:set`). CI fails if a Stripe secret
  key or private key appears in tracked files or in `build/web`.
- `build/`, `.dart_tool/` and `.flutter-plugins*` are gitignored. `.dart_tool/`
  contains the Chrome profile used by `flutter run -d chrome`, including Firebase
  Auth tokens after a local sign-in, so never force-add it.
- Use Flutter 3.47.7, the version CI pins. CI runs
  `flutter pub get --enforce-lockfile`, and running `pub get` on another Flutter
  version rewrites the SDK-pinned packages in `pubspec.lock`, which then fails CI.
- Lint infos are not fatal in CI yet; analyzer warnings and errors are.
- Tests run on the Dart VM, so code under test must not import web-only
  libraries (`package:web`, `dart:js_interop`). `main.dart` and `HomePage` need
  Firebase (the carousel calls Firebase Storage), so tests don't pump them.
  Widgets that use `AppServices` are pumped with `testApp()` from
  `test/support/fakes.dart`. The session cards have fixed widths, so page tests
  set a desktop-sized `tester.view`.
- Google blocks sign-in inside in-app browsers such as Instagram's, Facebook's,
  TikTok's and Pinterest's ("403 disallowed_useragent"). There the sign-in
  dialog explains how to open the page in Safari or Chrome instead.
- The Payment Link tags (`client_reference_id`, `locked_prefilled_email`) come
  from the URL, which anyone can edit, so they identify the payer for
  bookkeeping only. A booking entered by hand from them gives that uid access
  to the photos, so the README has the photographer check the uid's account
  against an email known from outside Stripe (the Stripe email comes from the
  same editable link).
- `firestore.rules` and `storage.rules` are the source of truth; deploying them
  replaces whatever is set in the console. Customers' photos live in
  `galleries/<bookingId>/` and are only handed out as signed URLs; never put
  them under `_admin/gallery/`, which is public.
- Rules aren't filters: the bookings query must be
  `where('uid', isEqualTo: uid)` or Firestore rejects it. Sort on the client;
  an `orderBy` would need a composite index (there's no `firestore.indexes.json`).
- CI deploys the backend as `github-deployer`, which deliberately has no
  direct permission to turn on APIs, read secret values or change IAM. The
  code and rules it deploys can still reach all data, so push access to `main`
  is the real boundary. Before merging a function that adds a secret, a
  non-secret param (needs a committed `functions/.env`), a new trigger type, a
  custom `serviceAccount` or a new API, prepare the project (README, "Before
  merging something new"), or the `deploy-backend` job fails. Once
  `BACKEND_DEPLOY_LIVE` is `true`, that failure also holds back the live site.
- The functions' runtime account has no broad access; `scripts/setup-functions-runtime.sh`
  grants what they need. A new function that reads other data needs a role added there.
- `getGalleryDownloadUrl` signs URLs through the IAM signBlob API, which needs
  Service Account Token Creator on the functions' runtime service account
  (README, "Deploying the backend").
- Placeholder content: lorem ipsum in `text_section.dart`; all three packages share
  the same bullets; session times, address and description in `session_card.dart`
  are hard-coded; footer social buttons only `print`; copyright says
  "Your Company Name"; `MaterialApp.title` is "Flutter Demo"; `pubspec.yaml` and
  `web/index.html` descriptions are "A new Flutter project."
- Selected date and time are not passed to Stripe or stored anywhere, so the
  app doesn't create bookings yet; they are entered by hand in the Firestore
  console until server-created Checkout Sessions write them.
- `CarouselExample._timer` is `late` and is only assigned after the Storage call
  completes, so disposing the widget before that throws.
