# AGENT.md

Guidance for AI coding agents (and humans) working in this repository.

## What this is

**Brookie Babies** is a Flutter **web** app: the booking and photo delivery site
for Brooke Stapleton Photography. Visitors see a full-bleed photograph with the
logo, a short introduction and a few more photographs, choose a session package
(Basic / Premium / Ultimate), pick a date and a time, and are sent to a Stripe
Payment Link to pay. Signed-in families see "Your sessions" and download their
photos as one zip. Admins (the studio) use an admin portal at `/#/admin` to
add ad hoc sessions for family and friends, upload photos, make them available
and choose the home page photos.

- Firebase project: `brookie-babies` (see `.firebaserc`)
- Hosting: Firebase Hosting, serving the static `build/web` output
- Stage: early MVP. Session times and package inclusions are placeholders (see "Known gaps").

Although the `android/`, `ios/`, `macos/`, `linux/` and `windows/` folders exist
(from `flutter create`), **only web is supported**:
`lib/firebase_options.dart` only configures web; every other platform throws
`UnsupportedError` at startup.

Always run and build with `-d chrome` / `flutter build web`.

## Tech stack

| Concern | Package |
|---|---|
| UI framework | Flutter 3.47.7 (Material 3), pinned in CI |
| Firebase bootstrap | `firebase_core` |
| Home page photos | `firebase_storage` behind `PortfolioService` (the file names chosen in Firestore `site/home`, in order, from `gs://brookie-babies.firebasestorage.app/_admin/gallery`; without them, that folder sorted by file name) |
| Design system | `lib/theme/brookie_theme.dart` (Print and Darkroom themes); Jost and Newsreader bundled as TTFs in `assets/fonts/` (no `google_fonts`) |
| Calendar | `table_calendar` |
| Payments | Stripe Payment Links via `url_launcher` |
| Auth | `firebase_auth`: Google sign-in (popup) behind `AuthService`; admins are accounts with the custom claim `admin: true` (`AuthService.isAdmin`) |
| Bookings | `cloud_firestore`: `bookings` collection behind `BookingService` (read-only for customers: their own by uid, and ad hoc sessions shared with their email) |
| Admin | `AdminService` + `FirebaseAdminService` (`cloud_firestore`, `firebase_storage`): ad hoc sessions, session photos, the home page library and `site/home`, written straight from the browser and guarded by the rules |
| File picking | The browser's `<input type=file>` through `package:web` (`lib/utilities/web_photo_picker.dart`), as `AppServices.pickPhotos`; no file-picker package |
| Photo downloads | `cloud_functions`: `getGalleryDownloadUrl` (in `functions/`) behind `GalleryService` |
| Backend | Cloud Functions for Firebase, TypeScript on Node 24 (`functions/`); Firestore and Storage security rules |
| Lints | `flutter_lints` (`analysis_options.yaml`, default rules) |

## User flow

1. `HomePage` gets photo links from `PortfolioService`: the file names an
   admin chose in Firestore `site/home`, in order, or, with none chosen or no
   answer within 3 s, the image files in Storage `_admin/gallery` sorted by
   name. `HomeHero` shows the first one
   full-bleed with the logo and a butter "Book a session" button that scrolls to
   the packages; `FeaturedPhotos` shows up to six more below the introduction.
   With no photos the hero sits on a quiet band with an ink button.
2. `Packages` → `PackageCard` "Choose Premium" → `Navigator.push(SchedulingPage(packageName))`.
   Coming back, that card is selected and reads "Continue with Premium".
3. `SchedulingPage` opens on the first day that still has times. The family
   picks a day in `BookingCalendar` and a time in `SessionList`; "Continue to
   payment" (disabled until a time is chosen) calls `navigateCheckout()`.
   Signed-out visitors get `showSignInDialog(toBook: true)` first (Google popup). It then opens the package's Stripe Payment Link
   (`services/payment_links.dart`) in the same tab, with
   `client_reference_id=<uid>` and `locked_prefilled_email=<email>` so the
   payment shows which account paid. This is interim: the plan is to replace
   Payment Links with Checkout Sessions created by a Cloud Function.

4. Account menu → "Your sessions" (`ProfilePage`, also at `/#/profile`) lists the
   user's `bookings`, split into upcoming and past: `watchBookings(user)` merges
   `where('uid', isEqualTo: uid)` with, when the user has an email,
   `where('status', isEqualTo: 'adhoc').where('email', isEqualTo: <lowercased email>)`
   (ad hoc sessions shared with them; that query failing counts as none). A
   paid or ad hoc session with
   `photosReady: true` has "Download all photos" (past ones without it
   say the photos are being edited; ad hoc ones have no payment tag): `getGalleryDownloadUrl`
   checks the booking belongs to the caller (its uid, or an ad hoc session's
   email matching the caller's verified Google email), zips `galleries/<bookingId>/` (cached
   in `gallery-zips/`), and returns a signed link that expires after an hour,
   opened in the same tab.

The account control (top right of the hero and of every page's top bar) signs
in and out at any time.

Admin flows (accounts with the `admin: true` claim, from `scripts/grant-admin.sh`):

5. Account menu → "Admin" (shown once `auth.isAdmin()` says so, between "Your
   sessions" and "Sign out") → `AdminPage.open`, which puts `AdminPage` over
   the home page; the named route `/admin` (`/#/admin`) opens it too. Every
   admin page wraps its body in `AdminGate`, which
   checks `isAdmin(refresh: true)` per uid and otherwise asks to sign in or
   says the account isn't an admin.
6. "Add a session" → `SessionFormPage` → `AdminService.createSession` (an ad
   hoc `bookings` doc: `status: 'adhoc'`, name, email, date, ...) → replaced by
   `AdminSessionPage` for the new id. A session card on Admin opens the same page.
7. `AdminSessionPage`: "Upload photos" → `pickPhotos(accept: 'image/*')` →
   `UploadQueue` (three at a time, names already there skipped, checked with
   `PhotoRules.sessionPhotoProblem`) → `uploadSessionPhoto` into
   `galleries/<id>/`. "Make photos available" (confirmed) →
   `setPhotosReady(id, true)`; "Hide photos" undoes it. "Copy message" copies
   `AdminSessionPage.shareMessage`: the `/#/profile` link and the Google
   account to sign in with. Ad hoc sessions also have "Edit details"
   (`SessionFormPage(session:)` → `updateSession`) and "Delete session"
   (`deleteSession`: hide, delete the photos and the cached zip, then the doc;
   back to Admin with `AdminPage.returnWithNotice`). Paid bookings only get
   photos and readiness: their details stay in the console.
8. "Edit home page photos" → `HomePhotosAdminPage`: `listHomeLibrary()` and
   `homePhotoNames()`; choose up to seven, order them (Move up / Move down /
   Remove), "Save home page" → `saveHomePhotos` (`site/home`) →
   `HomePage.reloadPhotos()`. Uploads use `pickPhotos(accept:
   'image/jpeg,image/png,image/webp')`, `PhotoRules.homePhotoProblem` and
   `uploadToHomeLibrary`.

Nothing in the app creates paid bookings yet: the Payment Links don't carry the date
or time. Until server-created Checkout Sessions write them, the photographer
adds them by hand in the Firestore console (fields in the README). Ad hoc
sessions are created in the admin portal.

A named route `/schedule` exists in `main.dart` but the main flow does not use
it. It has no package, so the page says to choose one first and offers "See
packages" (`HomePage.showPackages`), which goes home and scrolls to them.

## Conventions

- Imports in `lib/` use `package:brookie_babies/...`. Tests import shared
  helpers relatively (`../support/fakes.dart`).
- Widgets are mostly `StatelessWidget` with `const` constructors and `super.key`.
- Style everything through `lib/theme/brookie_theme.dart`: colors from
  `BrookieColors.of(context)` (no hex literals or `Colors.*` in widgets, except
  `Colors.transparent`), text from `Theme.of(context).textTheme` or `BrookieType`,
  spacing `BrookieSpace`, radii `BrookieRadius`, sizes `BrookieSize`, widths
  `BrookieBreakpoint` / `BrookieLayout`, motion `kBrookieStateDuration` /
  `kBrookieFadeDuration` (and honor `MediaQuery.disableAnimationsOf`). Check
  every change in both themes: Darkroom follows the device setting.
- Butter is only for the hero's button on the photograph, selected states (with
  a 1.5px ink ring) and the signed-in avatar. One ink primary button per view.
  Photographs have square corners and are never tinted or overlaid.
- Keyboard focus: buttons get the theme's ring (`brookieFocusSide`: a 2px gap,
  then a 2px ring; outlined buttons keep their edge under it via
  `FocusRingBorder`); custom controls use `FocusRing`, and controls on a
  photograph `FocusRing.onPhoto`. Controls focused without a key press (a
  dialog's first action, the account avatar) show their ring only while
  `KeyboardInput.lastWasKey`. Never remove a focus ring.
- The only colors outside `BrookieColors` are Google's, inside
  `GoogleSignInButton`, as Google's sign-in branding requires.
- Copy follows the design system's voice: sentence case, verb-first buttons that
  say what happens, one name per action through a flow, times from
  `SessionTime` ("9:00–9:30 am", "9:00 am"), dates from `formatDayHeading` /
  `formatDayShort`, prices from `SessionPackage.priceLabel`, typographic
  apostrophes (’), no exclamation marks in errors, and errors that say what
  happened and how to fix it.
- Put new screens in `pages/`, page sections in `components/`, reusable leaf
  widgets in `widgets/`.
- Logging uses `dart:developer`'s `log()`.
- Get services with `AppServices.of(context)`. Only `main.dart` touches
  `FirebaseAuth.instance` (and the other Firebase instances) and `launchUrl`.
  `package:web` is touched only by `main.dart` and
  `lib/utilities/web_photo_picker.dart`, which only `main.dart` imports. So
  everything else can be tested with the fakes in `test/support/fakes.dart`.
- Call `signInWithGoogle()` as the first thing in a tap handler, before any
  `await`, or the browser may block the popup. Don't switch to redirect
  sign-in: the site (web.app) and auth domain (firebaseapp.com) differ, which
  breaks redirects in current browsers.
- The same goes for `AppServices.of(context).pickPhotos(accept: ...)`: call it
  first in the tap handler, or the browser won't open the file picker. Never
  wait on its Future with the page blocked: browsers without the input's
  `cancel` event never complete it when the picker is cancelled.
- A page with work that leaving would lose (uploads running, unsaved changes)
  calls `LeaveWarning.set(this, true)` while it has it and
  `LeaveWarning.set(this, false)` in `dispose`, and guards back with a
  `PopScope` that asks with `showBrookieConfirm`. Any "Sign out" button uses
  `signOutWithWarning(context)`. Tests that touch it
  `tearDown(LeaveWarning.reset)`.
- Admin pages: `BrookieTopBar(showAdminLink: false)` and the body inside
  `AdminGate`. The gate only decides what the page shows; the rules decide
  what an admin can do.
- The client checks mirror the rules: `lib/services/photo_rules.dart`
  (`PhotoRules`, `SessionRules`) and `newSessionData()` / `sessionChanges()` in
  `lib/services/admin_service.dart` send exactly what `firestore.rules` and
  `storage.rules` accept, so a rule rejection only ever means an access
  problem. Change them together with the rules (each points at the other;
  `test/services/rules_mirror_test.dart` reads both rules files and fails when
  the keys, limits, types, packages or email pattern disagree), and keep
  `PhotoRules.homeMaxPhotos` = 1 + `FeaturedPhotos.maxCount` (a test checks
  it).
- One primary button per view and the photograph rules (square corners, never
  tinted, overlaid or badged: say a photo's state beside it) apply to the
  admin pages too. Their tests check each view at 320, 390 and 1440px in both
  themes with at most one `FilledButton`.

## Known gaps / gotchas

- **SECURITY: this repository is public.** A live Stripe secret key used to be
  hard-coded in `lib/main.dart` and was also committed inside `build/` and
  `.dart_tool/` output. It has been removed from the tracked files but remains in
  git history, so it must be rolled in the Stripe dashboard. Never add secrets,
  service account keys or Stripe keys to this repo; server-side secrets belong in
  Secret Manager (`firebase functions:secrets:set`). CI fails if a Stripe secret
  key or private key appears in tracked files or in `build/web`.
- `build/`, `.dart_tool/` and `.flutter-plugins*` are gitignored. `.dart_tool/`
  contains the Chrome profile used by `flutter run -d chrome`, including Firebase
  Auth tokens after a local sign-in, so never force-add it.
- Use Flutter 3.47.7, the version CI pins. CI runs
  `flutter pub get --enforce-lockfile`, and running `pub get` on another Flutter
  version rewrites the SDK-pinned packages in `pubspec.lock`, which then fails CI.
- Lint infos are not fatal in CI yet; analyzer warnings and errors are.
- Tests run on the Dart VM, so code under test must not import web-only
  libraries (`package:web`, `dart:js_interop`). `main.dart` needs Firebase, so
  tests don't pump it; `HomePage` is pumped with a `FakePortfolioService`.
  Widgets that use `AppServices` are pumped with `testApp()` from
  `test/support/fakes.dart` (pass `brightness: Brightness.dark` for Darkroom);
  admin pages with `pumpAdminPage()` from `test/support/admin_test_app.dart`.
  Layout tests set `tester.view.physicalSize` per width; `widget_test.dart`
  loads the real Jost TTFs, because whether the package cards sit side by side
  depends on real text widths.
- Because tests run on the VM, the real file picker (`web_photo_picker.dart`)
  and the `beforeunload` warning in `main.dart` have no tests: check them by
  hand in Chrome and Safari (picking, cancelling the picker, closing the tab
  during an upload).
- Google blocks sign-in inside in-app browsers such as Instagram's, Facebook's,
  TikTok's and Pinterest's ("403 disallowed_useragent"). There the sign-in
  dialog explains how to open the page in Safari or Chrome instead.
- The Payment Link tags (`client_reference_id`, `locked_prefilled_email`) come
  from the URL, which anyone can edit, so they identify the payer for
  bookkeeping only. A booking entered by hand from them gives that uid access
  to the photos, so the README has the photographer check the uid's account
  against an email known from outside Stripe (the Stripe email comes from the
  same editable link). For the same reason a hand-entered paid booking must
  never get `status: 'adhoc'`: its email would become the key to the photos.
- `firestore.rules` and `storage.rules` are the source of truth; deploying them
  replaces whatever is set in the console. Customers' photos live in
  `galleries/<bookingId>/` and are only handed out as signed URLs; never put
  them under `_admin/gallery/`, which is public.
- Rules aren't filters: the bookings queries must be exactly
  `where('uid', isEqualTo: uid)` and
  `where('status', isEqualTo: 'adhoc').where('email', isEqualTo: <email trimmed and lowercased>)`
  (and the guest's token must have `email_verified`), or Firestore rejects the
  whole query. Sort on the client; an `orderBy` would need a composite index
  (there's no `firestore.indexes.json`).
- `status: 'adhoc'` is matched exactly (no trimming or case folding) by the
  rules, `canDownload` in `functions/src/gallery.ts` and `Booking.fromMap`; a
  hand-typed `" adhoc"` or `"Adhoc"` is unreadable in the app and shared with
  nobody. Ad hoc sessions are made in the portal, which writes the email
  trimmed and lowercase.
- Admin access is the `admin` claim in the caller's ID token. `isAdmin()`
  refreshes the token on its first check per uid in a page load, so a grant
  shows after a refresh. Revoking (`--revoke`) can't end a token already
  issued: an open sign-in keeps admin access, in the app and in the rules,
  until it expires, within an hour.
- `_admin/gallery` is public: anyone can list it and download every file, on
  the home page or not. The listing is needed by the fallback for a missing
  `site/home` (and by the site that's live now). Locking it down is on the
  TODO list.
- `StoragePortfolioService` waits at most 3 s
  (`homePhotoNamesTimeLimit`) for `site/home`, then shows the folder by name, so
  a slow or failing read never holds up the hero. An empty `photos` list means
  no photos, not the fallback.
- Uploads never overwrite: `storage.rules` has no `update`. `UploadQueue`
  skips names already in the destination or the queue; an upload refused with
  `unauthorized` whose object turns out to exist (`getMetadata`) is reported
  as already there, not as a missing claim. Object names come from
  `PhotoRules.safeObjectName`. To replace a photo, delete it first.
- Admin Firestore writes give up after 20 s (offline, the web SDK would wait
  for good) and say the change may still be saved. `deleteSession` hides the
  photos, deletes them and the cached zip, then the doc, and counts a session
  already gone as deleted.
- CI doesn't evaluate the rules: it has no emulator, and
  `FirebaseAdminService` is tested against the in-memory fakes in
  `test/support/fake_firebase.dart`, which don't apply them
  (`rules_mirror_test.dart` only compares their limits with the Dart). Before
  deploying a rules change, compile it with
  `firebase deploy --only firestore:rules,storage --dry-run` and run
  `bash scripts/test-rules.sh` (the cases in `rules-tests/` against the
  read-only Rules API, `projects/brookie-babies:test`; it needs the owner's
  `gcloud auth login`), adding cases for what changed. Never test rules by
  writing to the live project.
- Deploy order: the site relies on the new rules and function, not the other
  way round, so deploy the backend before (or with) the site. A site that goes
  first gets its guest query and `site/home` read refused (both fall back
  harmlessly) and every admin read and write denied (README, "Deploy order").
- CI deploys the backend as `github-deployer`, which deliberately has no
  direct permission to turn on APIs, read secret values or change IAM. The
  code and rules it deploys can still reach all data, so push access to `main`
  is the real boundary. Before merging a function that adds a secret, a
  non-secret param (needs a committed `functions/.env`), a new trigger type, a
  custom `serviceAccount` or a new API, prepare the project (README, "Before
  merging something new"), or the `deploy-backend` job fails. Once
  `BACKEND_DEPLOY_LIVE` is `true`, that failure also holds back the live site.
- The functions' runtime account has no broad access; `scripts/setup-functions-runtime.sh`
  grants what they need. A new function that reads other data needs a role added there.
- `getGalleryDownloadUrl` signs URLs through the IAM signBlob API, which needs
  Service Account Token Creator on the functions' runtime service account
  (README, "Deploying the backend").
